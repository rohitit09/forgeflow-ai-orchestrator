# Command: execute-plan

Thin entrypoint. All logic lives in `skills/execute-plan/SKILL.md` (pre-flight) and `agents/orchestrator.md` (loop). Read them and follow them — do not re-describe steps here.

**Arguments:** $ARGUMENTS  ·  `<plan-id>` = directory name under `plans/`

## Two layers

1. **`skills/execute-plan/SKILL.md`** — pre-flight (load, validate, Jira gate, feature branch, worktrees, provisioning), then dispatches the orchestrator, then handles **delivery** (PR push, `gh pr create`, Jira comment) after the orchestrator returns `delivery_pending`. Same skill handles both `/execute-plan` (fresh) and `/resume-plan` (resume) — it decides which flow from `state.status`.
2. **`agents/orchestrator.md`** — dispatched once, owns the DAG loop end-to-end: READY scan, specialist dispatch, persist BEFORE and AFTER every transition, autonomous failure routing (no human gates in the loop), per-task commit, then sets `state.status = "delivery_pending"` and returns. Never touches PR or Jira.

Crash safety is enforced in the orchestrator's Persistence contract plus the skill's atomic-rename writes. If anything dies (server, token, agent), run `/resume-plan <plan-id>` — the same skill rebuilds truth from `state.json` + `events.jsonl` + `git log` and re-dispatches the orchestrator (or, if the crash happened after the DAG landed, picks up delivery from `delivery_pending`).

## Steps

1. Read `skills/execute-plan/SKILL.md` and run it against `$ARGUMENTS`. The skill takes it from there — pre-flight → orchestrator dispatch → delivery → final report.

## What it executes

Plans generated by `/create-plan`. They live at `plans/<plan-id>/`:

- `plan.json` — task DAG. Task fields: `id`, `title`, `repo`, `type`, `description`, `depends_on`, `parallelizable`, `files_touched`. Types: `architecture | development | test | review | debug`.
- `state.json` — execution state (`approved` after `/create-plan`; extended by pre-flight and mutated at every transition by the orchestrator).
- `plan.md` — human summary.

The orchestrator maps `task.type` to a specialist agent internally — no user prompt for `review` or `architecture` tasks.

## Constraints

- Never push to a branch listed in a repo's `protected_branches`.
- Never write outside a task's declared `files_touched`.
- **No user prompts inside the DAG loop** — task routing, review verdicts, and failure handling are all autonomous or end in safe-stop. The skill has two narrow prompts outside the loop: a **Jira gate** at pre-flight if the plan has no key attached, and **resume blocker-resolution prompts** in Step 3a. That is all.
- Read `runtime.test_cmd` from `config/repositories.json` — never guess.
- `state.json` writes are atomic-rename; `events.jsonl` is append-only. The run must be resumable from disk alone.
